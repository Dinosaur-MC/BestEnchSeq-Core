## 1. 项目概述与目标

### 1.1 项目定位

BestEnchSeq-Core 是一个计算 Minecraft 最优魔咒顺序/锻造序列的 C++ 核心库。给定目标物品和一组可用物品（附魔书、附魔装备等），计算出消耗经验等级最少的铁砧锻造步骤序列。

### 1.2 核心目标

- 为玩家提供可执行的锻造方案，最小化总经验消耗
- 支持原版 Minecraft 所有魔咒
- 通过外部数据文件支持模组/自定义魔咒和装备，无需修改代码
- 提供清晰的程序化输出（纯文本 + JSON），便于分享和二次处理

### 1.3 适用范围

| 范围     | 包含                                                  | 不包含                     |
| -------- | ----------------------------------------------------- | -------------------------- |
| 魔咒数据 | 原版 + 自定义魔咒注册、兼容性、等级、费用             | 魔咒效果逻辑               |
| 装备数据 | 原版 + 自定义装备注册、装备分类                       | -                          |
| 物品管理 | 附魔书、已附魔装备输入，自动选品                      | -                          |
| 锻造计算 | 魔咒合并、费用计算（JE/BE）、方案生成                 | 高性能算法优化（后续版本） |
| 数据解析 | 外部数据文件读取、格式识别、标签解析                  | -                          |
| 格式转换 | 数据格式间转换（原生 JSON ↔ CSV ↔ MC 官方）、数据导出 | -                          |
| 输出导出 | 纯文本详细版、纯文本紧凑版、JSON 双向序列化           | -                          |
| 网络服务 | -                                                     | RESTful API（后续版本）    |

### 1.4 目标用户

- **玩家**：输入锻造需求和可用物品，获取最优锻造方案
- **模组包作者**：通过数据文件注册自定义魔咒和装备
- **工具作者**：通过 JSON 输出将本工具集成到其他系统中

## 2. 用户故事

### 2.1 玩家

**US-01 — 达成目标魔咒**

作为玩家，我想输入目标物品（可为无魔咒的空白装备、已有部分魔咒的装备，或附魔书）和期望的魔咒列表，由程序自动识别目标状态并计算出最优锻造方案，以实现目标效果。

**US-02 — 从库存锻造**

作为玩家，我想输入当前物品库存（附魔书、附魔装备等）和目标物品（装备或附魔书），由程序按物品优先级自动选取最优组合，输出锻造方案。

### 2.2 模组包作者

**US-03 — 注册自定义魔咒**

作为模组包作者，我想通过编辑魔咒数据文件来注册模组魔咒，让程序能正确处理自定义魔咒的兼容性、等级限制和费用计算。

**US-04 — 注册自定义装备**

作为模组包作者，我想通过编辑装备数据文件来注册模组装备，让程序能正确判断哪些魔咒可应用于自定义装备。

### 2.3 工具作者

**US-05 — 导出计算结果**

作为玩家或工具作者，我想将计算结果导出为纯文本（人类可读版和机器解析版）或 JSON，以便在游戏中参考或集成到其他工具中。

## 3. 交互方式

采用 **CLI 参数 + 输入文件混合** 模式：

```
besq [options]
```

**两种模式对应两种使用场景：**

```
# 达成目标魔咒：目标物品及期望魔咒写在内联括号中，程序自动生成所需附魔书
besq --target "diamond_sword[sharpness=5,knockback=2]"

# 装备升级：--target 括号内为期望魔咒，--source 为装备当前已有魔咒（起点状态）
besq --target "diamond_sword[sharpness=5,knockback=2]" --source "sharpness=3"

# 库存锻造：--input 提供自包含 JSON 任务（内含 target/items/algorithm/profile），
# 单独使用即可配置一次库存模式求解；--mode inventory 与 --target 为可选项（JSON 已携带时）
besq --input task.json

# 附魔书目标：book 也可作为 target（MC 中附魔台把 book 转成 enchanted_book）。
# "book" 与 "enchanted_book" 等价并归一化为 enchanted_book（book 本身无法承载魔咒）。
# 书无耐久（durability 恒为 0），但像铁砧物品一样携带 prior_penalty。
besq --target "enchanted_book[sharpness=5,knockback=2]"
besq --target "book[mending=1,unbreaking=3]" --source "unbreaking=1"
```

**通用选项：**

- `-h, --help` — 帮助信息
- `-V, --version` — 版本信息
- `-v, --verbose` — 完成时显示算法诊断计数器
- `--algorithm <name>` — 搜索算法：dp_merge (默认), hamming；astar/dfs 需经 `--algo-dir` 插件加载；库存模式默认使用 hamming
- `--target <spec>` — 目标物品及其期望魔咒（内联 `[魔咒列表]` 为锻造目标）；与 --export 二选一。装备 id 之外还接受 `book`/`enchanted_book`（归一化为 `enchanted_book`）作为附魔书目标，接受任意魔咒且无耐久
- `--source <魔咒列表>` — 装备当前已有魔咒（起点状态，装备升级场景），格式 `[命名空间:]<ID>=<等级>`；库存模式下不支持
- `--mode <direct|inventory>` — 运行模式（默认 direct）
- `--input <文件路径>` — 自包含 JSON 任务文件（内含 `target`/`items`/`algorithm`/`profile`）；单独指定即配置一次库存模式求解（隐式进入 inventory 模式），`--mode inventory`/`--target` 为可选项（JSON 已携带时）; `--input -` 从 stdin 读取任务内容
- `--import <文件列表>` — 导入数据文件到活跃 profile（逗号分隔多文件；自动识别 JSON/CSV/MC Official 格式）
- `--edit <ops>` — 运行前修改活跃 profile 的数据，格式 `<target>:<action>,<id>[,<field>=<val>...]`（分号分隔多操作；目标 ench|eq|cat，动作 add|mod|rm）
- `--export <路径>` — 导出活跃 profile 的数据到文件（.json / .csv）
- `--profile <key>` — 激活任意字符串 key 的 profile（默认激活内置根 `builtin:vanilla`）
- `--profile-dir <目录路径>` — 覆盖默认 `<cwd>/profiles` 扫描目录（native JSON/CSV 文件 + datapack 子目录）
- `--publish <key>` — 将 profile 的有效视图拍平为自包含 JSON 文件（`--publish-version <v>`、`--publish-tag <t>` 可选）
- `--platform <java|bedrock|auto>` — 目标平台（默认 auto，auto 表示同时考虑两平台差异）
- `--output <文件路径>` — 输出文件（默认 stdout）
- `--format <text|compact|json>` — 输出格式（默认 text）
- `--solutions <N>` — 最大输出方案数（默认 1，0 表示不限，最大 128）
- `--config <配置项>` — 运行时配置，格式 `key=value`，支持 `ignore-penalty-cost`、`ignore-repair-cost` 的 `true|false`
- `--memory <MB|auto>` — AStar（插件）搜索内存预算（默认 auto）
- `--max-time <秒>` — 搜索超时时间（0 = 不限，默认 0）
- `--lang <zh_CN|en_US>` — 界面语言（默认自动检测系统语言；可通过 `BESQ_LANG` 环境变量覆盖）

**参数值格式：**

魔咒列表（`--source`、内联魔咒）统一使用 `=` 作为等级分隔符，以规避命名空间 `:` 的冲突：

| 写法                           | 含义                                           |
| ------------------------------ | ---------------------------------------------- |
| `sharpness=5`                  | 魔咒 `sharpness`，等级 5                       |
| `minecraft:sharpness=5`        | 命名空间 `minecraft`，魔咒 `sharpness`，等级 5 |
| `thermalfoundation:excavate=3` | 自定义命名空间魔咒                             |

同时向下兼容 `:` 分隔等级（仅限无命名空间的简写形式）：`sharpness:5` 等价于 `sharpness=5`。含命名空间的魔咒必须使用 `=`，如 `minecraft:sharpness=5`。

**输入文件（`--input`）格式示例（JSON）——自包含任务：**

```json
{
    "target": {
        "item": "diamond_sword",
        "enchants": [
            { "id": "sharpness", "level": 5 },
            { "id": "knockback", "level": 2 }
        ]
    },
    "items": [
        {
            "type": "book",
            "enchants": [ { "id": "sharpness", "level": 5 } ],
            "prior_penalty": 0,
            "priority": 1
        },
        {
            "type": "book",
            "enchants": [ { "id": "knockback", "level": 2 } ],
            "prior_penalty": 1,
            "priority": 2
        },
        {
            "type": "equipment",
            "id": "diamond_sword",
            "enchants": [],
            "prior_penalty": 0,
            "durability": 1561,
            "priority": 10
        }
    ],
    "algorithm": "hamming"
}
```

- `target`（必填）：期望最终状态，`item` 为目标装备 id（或 `book`/`enchanted_book` 附魔书目标），`enchants` 为期望魔咒列表
- `items`：可用物品池，每件包含 `type`（`"book"` 附魔书 / `"equipment"` 装备）、`id`（仅 equipment）、`enchants`、`prior_penalty`、`priority`、`durability`（仅 equipment）
- `enchants`：魔咒列表，格式为 `[ { "id": "...", "level": N }, ... ]`。`id` 可用简写（`sharpness` 等价于 `minecraft:sharpness`）
- `prior_penalty`：前次铁砧惩罚次数，非负整数
- `durability`：（仅 equipment）当前耐久度，缺省或 ≤0 时等于最大耐久度
- `priority`：可选字段，数值越小优先级越高（越优先被选为牺牲物品）。仅 inventory 模式下生效。未指定时默认 99
- `algorithm`（可选）：指定求解算法，缺省时库存模式默认 `hamming`
- `profile`（可选）：激活指定 profile 后再解析任务（CLI 显式 `--profile` 覆盖之）
- 根级装饰字段（`name`/`description`/`author`/`version`）已移除——任务自包含于 `target`+`items`（旧格式文件若缺 `target` 将报 `inventory_schema_error`，需补 `target` 后迁移）

简单场景（少量魔咒、无复杂库存）可完全通过 CLI 参数完成；复杂场景（大量库存物品、自定义数据包）使用输入文件。

**库存模式（inventory）语义：**

- `target` 的期望最终状态来自 JSON `target` 块（CLI `--target` 存在时覆盖之）；与 direct 模式一致
- 装备当前状态（起点）取自 `--input` 文件中与目标同 id 的 `equipment` 条目；文件中无该条目时从空白装备开始
- 可用物品池：附魔书 + 与目标同 id 的装备；**排除**其余物品（非附魔书且非目标物品 ID，由 `CompactAdapter` 强制执行）
- 算法域的 resolver（`InventoryResolver`）按 `priority` 排序并选取最优组合，随后求解锻造路径

**已知限制（沿用，暂不修复）：**

- 库存求解要求 `items` 中存在目标 id 的基准装备：纯书任务（物品池无装备）会报告 `目标不可达`——`DefaultResolver` 只返回牺牲物品，且 hamming 在 `items.size() <= 1` 时以 `CompleteNoSolution` 退出
- **F7**：CLI `--target` 无法挽救格式错误的 JSON `target`——JSON `target` 在 `build_inventory` 阶段（CLI 覆盖生效前）即被校验，故错误在 CLI 覆盖被咨询之前抛出

**UI-FR-01 CLI 参数解析**

解析命令行参数，构建运行配置。支持完整参数校验和友好的错误提示。

**UI-FR-02 输入文件解析**

读取并解析 JSON 格式的输入文件，与 CLI 参数合并。CLI 参数优先级高于输入文件对应字段。

**验收标准**

- 所有参数缺失或格式错误时报告明确错误信息
- `--mode` 参数决定运行模式（默认 direct），影响其他参数的解析逻辑
- 输入文件与 CLI 参数可组合使用
- `--help` 输出完整的参数说明和使用示例

## 4. 功能需求

### 4.1 魔咒数据管理

**ENCH-FR-01 魔咒注册**

系统内置原版 Minecraft 所有魔咒的元数据，启动即加载。每条魔咒数据包含：

- 魔咒 ID
- 显示名称
- 最高等级
- 费用倍率（装备乘数 / 附魔书乘数）
- 适用平台（Java/Bedrock/All）
- 适用装备类别
- 互斥魔咒列表
- 限制等级/条件

**ENCH-FR-02 自定义魔咒**

支持通过外部数据文件注册额外魔咒。支持三种数据格式：

- 原生 JSON（单文件整合魔咒 + 装备 + 标签 + 元数据）
- 原生 CSV（分为 enchantments.csv 与 equipments.csv）
- MC 官方数据驱动格式（`data/<命名空间>/enchantment/<魔咒>.json`）

**ENCH-FR-03 平台差异**

支持 Java 版和 Bedrock 版的魔咒规则差异：

- 费用计算公式差异（JE：基于最终等级，互斥+1；BE：基于等级差值，互斥+0）
- 附魔书作为牺牲物品时的费用算法差异
- 横扫之刃仅存在于 Java 版
- 部分魔咒的平台乘数差异（如穿刺 Impaling）通过数据文件中的 `multiplier` 字段 + 算法层的 JE/BE 公式联合处理

**验收标准**

- 内置魔咒列表完整无误，对齐 MC Wiki 数据
- 加载自定义魔咒文件后，程序能正确识别并应用其规则
- 切换平台后，费用计算和兼容性行为相应变化
- 三种数据格式均能正确加载，可混合使用

### 4.2 装备数据管理

**EQP-FR-01 装备注册**

系统内置原版装备类型（头盔、胸甲、护腿、靴子、剑、弓、弩、三叉戟、钓鱼竿、盾牌、锄、斧、镐、锹等）及其魔咒适用规则，包含装备分类（盔甲、武器、工具等）。

**EQP-FR-02 自定义装备**

支持通过外部数据文件注册自定义装备。格式同自定义魔咒的三类数据格式（原生 JSON / 原生 CSV / MC 官方格式）。

**EQP-FR-03 装备分类**

支持按类别组织装备，类别继承关系明确。装备类别决定了哪些魔咒可应用于该装备。

**EQP-FR-04 格式转换与导出**

支持装备数据在不同格式间的相互转换：

- 原生 JSON ↔ 原生 CSV
- 原生 JSON/CSV → MC 官方格式（按目录结构导出）
- MC 官方格式 → 原生 JSON/CSV

**验收标准**

- 内置装备列表完整
- 自定义装备正确读取并参与魔咒适用性判断
- 装备分类体系正确
- 三种格式间的双向转换保持数据完整无损

### 4.3 物品库存管理

**INV-FR-01 物品输入**

支持通过自包含任务 JSON 的 `items` 块输入一个或多个可用物品（附魔书、已附魔装备），每件物品包含：

- 魔咒集合（含等级）
- 前次铁砧惩罚次数
- 耐久度
- 附魔书或装备类型
- 优先级 priority（可选，仅 inventory 模式生效，数值越小越优先）

**INV-FR-02 目标输入**

`target` 可来自自包含任务 JSON 的 `target` 块（`item` + `enchants`），也可来自 CLI `--target`（CLI 存在时覆盖 JSON）。目标物品可为无魔咒的空白装备、已有部分魔咒的装备，或附魔书；另含期望的最终魔咒列表。

**INV-FR-03 魔咒补全（US-01）**

在 direct 模式下，根据目标物品的当前状态自动计算所需附魔书：

- 目标无魔咒 → 为所有期望魔咒生成对应附魔书
- 目标已有部分魔咒 → 计算差异，仅生成缺失或等级不足的附魔书

**INV-FR-04 自动选品（US-02）**

库存锻造模式下，按输入文件中每件物品的 `priority` 值从可用物品中自动选取最优组合。`priority` 值越小越优先被选为牺牲物品。

**验收标准**

- direct 模式下，程序自动识别目标有无魔咒，无需用户指定子模式
- 自动补全生成的附魔书满足目标所有魔咒要求
- 差异计算正确识别已装备魔咒与目标的差距
- 自动选品参照 priority 值选取组合，同 priority 下选取总消耗最小的方案

### 4.4 锻造计算

**FORGE-FR-01 合并规则**

实现铁砧合并的核心规则：

- 魔咒兼容性检测（互斥检查）
- 魔咒适用性检测（魔咒是否可应用于目标物品的装备类型）
- 等级合并规则（牺牲高于目标 → 升至牺牲级；同级 → 升一级；低于 → 不变）
- 不可合并情况判断

**FORGE-FR-02 费用计算**

按所选平台（Java/Bedrock）计算每次合并的经验等级费用：

- 魔咒合并费用（基于魔咒乘数与等级）
- 前次铁砧惩罚费用（`惩罚_目标 + 惩罚_牺牲`）
- 耐久度合并费用（耐久不满时 +2 级）
- 附魔书作为牺牲物品时不产生耐久费用，使用书乘数
- 附魔书作为目标物品时的书乘数规则
- 总费用上限：生存模式固定 39 级上限。提供运行时配置选项（`--config` 提供 `ignore-penalty-cost=true|false`、`ignore-repair-cost=true|false` 配置项）以允许模组突破相关限制

**FORGE-FR-03 方案生成**

根据输入的物品集合，生成一个或多个可行的铁砧操作序列，每一步指定：

- 目标物品
- 牺牲物品
- 操作类型（合并魔咒/耐久修复/重命名）
- 操作消耗（经验等级 + 经验值）
- 结果物品的完整状态

**FORGE-FR-04 最优方案**

在所有可行方案中，按总经验消耗排序，选取消耗最少的序列。可配置最大输出方案数（默认输出最优的一个）。

**验收标准**

- 合并规则与 MC Wiki 完全一致（JE/BE 版本）
- 费用计算结果与游戏内实测一致
- 方案可完整逆向还原为锻造步骤
- 方案在给定约束下是最优或近似最优
- 求解路径不唯一时，可输出多个方案

### 4.5 自定义扩展

**EXT-FR-01 外部数据加载**

启动时从指定路径加载魔咒和装备的自定义数据文件，与内置数据合并。支持三种格式混合加载。

**EXT-FR-02 标签系统**

支持 MC 官方的 `#<命名空间>:<标签名>` 语法引用标签，用于互斥组和物品分类。标签从数据包目录加载。

**EXT-FR-03 元数据**

原生 JSON 格式包含元数据：名称、描述、作者、版本号、依赖列表（`dependencies`，字符串列表，传递解析）。

**EXT-FR-04 Datapack 加载**

支持把真实 MC 数据包（datapack）加载为一个 profile：

- 通过 `pack.mcmeta` 检测（profile key = `pack.id` 或文件夹名，verbatim 保留）
- 解析真实 MC 1.21+ 格式（单字符串/数组 `supported_items`、`slots`、`tag replace`、`anvil_cost`）
- 一个 datapack 的多个命名空间 `data/<ns1>/`、`data/<ns2>/`（含覆盖 vanilla 的 `data/minecraft/`）聚合进这一个 profile
- 默认扫描 `<cwd>/profiles/`（`--profile-dir` 覆盖），`--profile <key>` 激活任意字符串 key

**EXT-FR-05 Profile 依赖与发布**

支持 profile 依赖图（`dependencies` 传递解析 + 环检测）、有效视图（拓扑合并 + TagResolver）、版本化发布（`--publish` 拍平有效视图为自包含 JSON，内嵌 `version`/`release_tag`）。

**验收标准**

- 外部数据正确合并到注册表
- 标签引用正确解析展开
- 数据文件格式错误时报告明确的错误信息
- datapack 目录可被识别并加载为 profile，其自定义命名空间与 vanilla 覆盖均生效
- 依赖链正确解析（拓扑序），环被拒绝；发布文件自包含且含版本信息

### 4.6 结果输出

**OUT-FR-01 纯文本详细版**

输出人类可读的锻造方案：

- 头部：方案名称、模式、平台、总消耗、峰值单步、输入摘要
- 主体：步骤列表（`目标 + 牺牲 -> 结果`，含消耗）

**OUT-FR-02 纯文本紧凑版**

输出机器可解析的紧凑格式：

- 行首元数据（`#KEY=VALUE`）
- 每步定界符分隔字段
- 物品编码紧凑格式

**OUT-FR-03 JSON 输出**

输出结构化 JSON，满足双向序列化/反序列化：

- 完整输入摘要
- 每步输出物品的所有 public 字段（装备、魔咒、铁砧惩罚、耐久）
- 总消耗和每步明细
- 算法元数据
- JSON 格式可还原为程序对象

**验收标准**

- 三种输出格式内容一致
- JSON 输出可完整反序列化为 `EnchSolution` 对象
- 紧凑格式可被程序稳定解析
- 详细格式对人类可读、可直接用于游戏操作

| 紧凑注册表   | `EnchReg`         | `domain/algorithm/registries/` | O(1) 冲突矩阵，预计算乘数/最大等级 |
| 方案装配     | `CompactAdapter`   | `domain/orchestration/components/` | 从算法输出组装 Solution（recall）              |
| EXP 计算     | `ExpCalculator`    | `common/utils/`  | 经验等级与经验值的换算                           |
| 数据文件解析 | `NativeJsonParser`/`NativeCsvParser`/`McOfficialParser` | `domain/business/parsers/` | 读取外部数据文件，自动识别格式，产出 DTO |

| 结果格式化   | `OutputFormatter` | `domain/orchestration/components/` | 将 Solution 格式化为文本/紧凑/JSON             |
| 数据加载     | `ProfileLoader`   | `domain/business/loaders/` | Profile 加载/导出，委托 FormatDetector 识别格式 |
| 注册表管理   | `ProfileManager`/`RegistryHelper` | `domain/business/` + `domain/business/components/` | Profile 生命周期/依赖图/有效视图/发布 + 注册表集合运算/筛选/验证 |
| 文件格式检测 | `FormatDetector`  | `domain/business/components/` | 文件格式识别（JSON/CSV/MC Official）+ 分发 |

### 5.2 关键映射关系

- 每个 `Item` 可持有零或一个 `Equipment`（为空时表示为附魔书）
- `EnchSet` 依赖全局 `EnchInfo` 注册表进行兼容性和费用判断
- 适用性判定：魔咒 `supported_items`（`#tag` 或具体物品 ID）∩ 物品所属 tag（`tags_of(item)`）
- `Solution` 由 orchestration 层通过 `CompactAdapter::recall()` 组装，包含 `EnchStep` 列表
- Interface resolvers 层负责输入的验证和转换，CompactAdapter 负责 domain ↔ compact 转换

### 5.3 数据流

```
[数据文件] ──→ FormatDetector::detect() / parse()
                 ├── NativeJson  → EnchantmentData[] + EquipmentData[]
                 ├── NativeCsv   → EnchantmentData[]
                 └── McOfficial  → EnchantmentData[] + EquipmentData[]
                                            │
                                RegistryLoader::from_dto()
                                            │
                                            ▼
                                Profile (业务域一等公民)
                                ├── tags() → TagRegistry
                                ├── eq()   → EquipmentRegistry
                                └── ench() → EnchantmentRegistry

[用户输入] ──────→ ItemResolver / InventoryResolver ──→ AlgorithmInput
                                                              │
                                                              ▼
                                                     AlgorithmExecutor
                                                     ├─ IAlgorithm (策略)
                                                     ├─ IForgeEngine (锻造规则)
                                                     └─ ExecutionContext (暂停/取消/流式)
                                                              │
                                                              ▼
                                                     CompactAdapter::recall()
                                                              │
                                                              ▼
                                                     OutputFormatter ──→ [文本/紧凑/JSON]
```

## 6. 扩展机制

### 6.1 数据格式支持

**格式 A — 原生 JSON**

单文件整合，包含元数据、魔咒、装备和标签定义：

```json
{
  "name": "MyCustomPack",
  "description": "Adds fantasy enchantments for RPG gameplay",
  "author": "AuthorName",
  "version": "1.0.0",
  "dependencies": ["builtin:vanilla"],
  "enchantments": [ ... ],
  "equipments": [ ... ],
  "tags": {
    "enchantment": { ... },
    "item": { ... }
  }
}
```

`dependencies` 声明直接依赖的 profile key（字符串列表），由 `ProfileManager` 传递解析（拓扑序 + 环检测）。

**格式 B — 原生 CSV**

分为两个文件：

- `enchantments.csv`
- `equipments.csv`

元数据以注释行或单独元数据文件承载。

**格式 C — MC 官方数据驱动格式**

按 `data/<命名空间>/enchantment/<魔咒>.json` 的目录结构组织，兼容原版数据包。从中提取：

- `anvil_cost` → 费用倍率
- `max_level` → 上限等级
- `exclusive_set` → 互斥魔咒列表（支持 # 标签引用，单字符串或数组）
- `supported_items` → 适用装备（支持 # 标签引用，单字符串或数组）
- `slots`、`tag replace` 等真实 1.21+ 字段亦被识别

标签从 `data/<命名空间>/tags/enchantment/` 和 `data/<命名空间>/tags/item/` 加载。

含 `pack.mcmeta` 的完整数据包目录可经 `--profile-dir` 扫描 / `load_datapack` 直接加载为一个 profile（见 EXT-FR-04），其下多个命名空间聚合进该 profile。

### 6.2 标签系统

所有格式统一使用 `#<命名空间>:<标签名>` 语法引用标签。Parser 层在加载数据时解析标签引用并展开为具体条目。

### 6.3 加载策略

- 启动时扫描指定数据目录；默认扫描 `<cwd>/profiles/`（`--profile-dir` 覆盖）
- 自动识别文件格式（JSON / CSV / MC 官方目录结构）
- 目录下含 `pack.mcmeta` 的子目录按 datapack 加载为 profile（多命名空间聚合，见 EXT-FR-04）
- 三种格式可混合加载
- 内置原版数据作为默认值（根 profile `builtin:vanilla`），外部文件追加或覆盖
- `--profile <key>` 激活指定 profile；依赖链（`dependencies`）传递解析，加载时对 `#tag`/物品引用做交叉验证（见 EXT-FR-05）
- 格式错误时报告明确的文件路径和错误信息

## 7. 输出格式规范

### 7.1 纯文本 — 详细版

人类可读的锻造方案，`A + B -> C` 格式。支持输出多个方案（求解路径不唯一时），方案间以 `=======` 分隔。

```
===========================================
  锻造方案 - 锋利 V + 击退 II + 火焰附加 II
===========================================
模式: 简单锻造
平台: Java版
方案: 1/2

总消耗: 27 等级 (136 经验值)
峰值单步: Step 3 - 10 等级 (67 经验值)

输入:
  目标物品: 剑 (无魔咒)
  可用物品:
    - 附魔书 (锋利 IV)
    - 附魔书 (锋利 III)
    - 附魔书 (击退 II)
    - 附魔书 (火焰附加 I)
-------------------------------------------
  Step 1: 附魔书(锋利 IV) + 附魔书(锋利 III) -> 附魔书(锋利 V)
          - 消耗: 4 等级 (9 经验值)

  Step 2: 剑 + 附魔书(锋利 V) -> 剑(锋利 V)
          - 消耗: 8 等级 (42 经验值)

  Step 3: 剑(锋利 V) + 附魔书(击退 II) -> 剑(锋利 V, 击退 II)
          - 消耗: 5 等级 (18 经验值)

  Step 4: 剑(锋利 V, 击退 II) + 附魔书(火焰附加 I) -> 剑(锋利 V, 击退 II, 火焰附加 I)
          - 消耗: 10 等级 (67 经验值)
-------------------------------------------
===========================================
  方案 2/2 (同消耗)
===========================================
...（不同顺序的步骤序列）
```

模式显示映射：`direct` → "简单锻造"，`inventory` → "库存锻造"。

物品状态标识：

- 装备：`<装备名>(<魔咒1> <等级>, <魔咒2> <等级>, ...)`，附加 `[铁砧惩罚 xN]` 和 `[耐久 N]`
- 附魔书：`附魔书(<魔咒1> <等级>, <魔咒2> <等级>, ...)`，附加 `[铁砧惩罚 xN]`
- 消耗为 0 等级时标记为 `(免费)`

### 7.2 纯文本 — 紧凑版

机器可解析的紧凑格式，行首元数据 + 定界符分隔字段：

```
#MODE=inventory
#PLATFORM=java
#SOLUTIONS=2
1|E;minecraft:sword;;P;0;D;-1|B;minecraft:sharpness:4;P;0|E;minecraft:sword;minecraft:sharpness:5;P;1;D;-1|4|9
2|E;minecraft:sword;minecraft:sharpness:5;P;1;D;-1|B;minecraft:knockback:2;P;0|E;minecraft:sword;minecraft:sharpness:5,minecraft:knockback:2;P;3;D;-1|5|18
===
1|E;minecraft:sword;;P;0;D;-1|B;minecraft:sharpness:4;P;0|E;minecraft:sword;minecraft:sharpness:5;P;1;D;-1|4|9
2|...
```

多方案时以 `===` 行分隔，`#SOLUTIONS=` 声明方案总数。每段第一个 `#` 开头的行可为该方案的元数据。

物品编码格式（使用 `;` 分隔字段，`:` 保留给命名空间 ID；`;` 内字段不使用 `:`）：

- 装备：`E;<装备ID>;<魔咒1ID>:<等级1>,<魔咒2ID>:<等级2>;P;<惩罚>;D;<耐久>`
- 附魔书：`B;<魔咒1ID>:<等级1>,<魔咒2ID>:<等级2>;P;<惩罚>`

每步格式（使用 `|` 分隔字段）：`<序号>|<目标物品编码>|<牺牲物品编码>|<结果物品编码>|<等级消耗>|<经验值消耗>`

### 7.3 JSON 格式

完整结构化 JSON，支持序列化与反序列化双向转换。支持输出多个方案：

```json
{
  "schema_version": "1.0",
  "mode": "inventory",
  "solutions": [
    {
      "rank": 1,
      "platform": "Java",
      "original_ench": [
        { "id": "sharpness", "level": 5 }
      ],
      "target_item": { <ItemStack> },
      "available_items": [ <ItemStack> ],
      "steps": [
        {
          "item_a": { <ItemStack> },
          "item_b": { <ItemStack> },
          "exp_level_cost": 4,
          "exp_cost": 9
        }
      ],
      "total_exp_level_cost": 27,
      "total_exp_cost": 136,
      "peak_level_cost": 10,
      "peak_exp_cost": 67,
      "max_cost_step_index": 2,
      "is_success": true,
      "metadata": {
        "algorithm_name": "default",
        "version": "1.0.0",
        "created_at": 1717200000,
        "computation_time": 12
      }
    }
  ]
}
```

每个 `solution` 对象包含完整的输入摘要和算法元数据，不依赖外层对象。
`max_cost_step_index` 为峰值消耗步骤在 `steps` 数组中的索引（0-based）。

`<ItemStack>` 序列化结构：

```json
{
    "equipment": {
        "id": "diamond_sword",
        "category": "sword",
        "name": "Diamond Sword",
        "max_durability": 1561
    },
    "enchantments": [
        { "id": "sharpness", "level": 5 },
        { "id": "knockback", "level": 2 }
    ],
    "prior_penalty": 1,
    "durability": 250,
    "is_book": false
}
```

附魔书序列化：`"equipment"` 为 `null`，`"is_book"` 为 `true`。

反序列化时，无命名空间的魔咒 ID 视为原版（`sharpness` 等价于 `minecraft:sharpness`）。
装备 ID 同理。

要求：`EnchStep` 的序列化与反序列化互为逆操作，确保输出可完整还原为程序对象。

## 8. 术语表

| 中文     | English            | 定义                                                                       |
| -------- | ------------------ | -------------------------------------------------------------------------- |
| 魔咒     | Enchantment        | Minecraft 中赋予装备的特殊效果                                             |
| 附魔     | Enchant (v.)       | 将魔咒应用于装备或书本的动作                                               |
| 附魔书   | Enchanted Book     | 已附魔的书本，可用作铁砧目标或牺牲物品                                     |
| 目标物品 | Target Item        | 铁砧界面左侧物品，锻造操作的基础（可为装备或附魔书）                       |
| 牺牲物品 | Sacrifice Item     | 铁砧界面右侧物品，锻造操作中被消耗的物品                                   |
| 铁砧惩罚 | Prior Work Penalty | 物品每次铁砧非重命名操作后累积的惩罚，公式 `2ⁿ − 1`                        |
| 经验等级 | Experience Level   | 玩家等级（游戏中显示的数字等级）                                           |
| 经验值   | Experience Points  | 等级对应的实际经验数值                                                     |
| 乘数     | Multiplier         | 魔咒在合并费用计算中的权重系数，装备和附魔书不同                           |
| 互斥     | Exclusive          | 多个不能共存于同一物品上的魔咒关系                                         |
| 数据包   | Data Pack          | Minecraft 官方扩展机制，用于自定义游戏内容                                 |
| 命名空间 | Namespace          | Minecraft 数据驱动中的唯一标识前缀（如 `minecraft:`）                      |
| 标签     | Tag                | Minecraft 中用于分组引用的 ID 集合（如 `#minecraft:exclusive_set/mining`） |
